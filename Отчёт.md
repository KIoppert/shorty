# Отчёт: shorty — сервис коротких ссылок

## 1. Доменная область

**shorty** — сервис сокращения ссылок. Пользователь регистрируется, вставляет длинный URL и получает короткий адрес вида `http://localhost:8080/aX9kQ2`. При переходе по короткому адресу сервис перенаправляет на исходный URL и записывает факт перехода.

Возможности:

- регистрация, вход и выход, удаление аккаунта;
- создание короткой ссылки со случайным кодом или собственным алиасом;
- название ссылки, срок действия, временное отключение;
- редактирование и удаление ссылок;
- статистика: общее число переходов, график за 14 дней, последние 20 переходов с источником (referrer) и типом устройства;
- генерация QR-кода для короткой ссылки.

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Бэкенд | Go 1.27, стандартный `net/http` (роутинг по шаблонам `GET /api/links/{id}`), `log/slog` |
| Доступ к БД | `jackc/pgx/v5` (пул соединений `pgxpool`) |
| Аутентификация | `golang-jwt/jwt/v5` (HS256), `golang.org/x/crypto/bcrypt` |
| QR-коды | `skip2/go-qrcode` |
| СУБД | PostgreSQL 17 |
| Фронтенд | HTML, CSS, JavaScript без фреймворков и сборки; шрифты Google Fonts |
| Веб-сервер фронтенда | nginx 1.29: раздаёт статику и проксирует API |
| Окружение | Docker, Docker Compose |

Взаимодействие фронтенда и бэкенда — HTTP/1.1 REST с JSON.

### Архитектура

```
браузер ──► web (nginx) ──┬── /, /assets/*  → статические файлы
                          └── /api/*, /{code}, /healthz → api (Go) ──► db (PostgreSQL)

migrate (Go, тот же образ, что у api) ──► db   (разовый запуск перед api)
```

## 3. Основные сущности

```
users 1 ──── * links 1 ──── * clicks
```

### User — пользователь

| Поле | Тип | Описание |
|---|---|---|
| `id` | BIGSERIAL | Идентификатор |
| `email` | TEXT, UNIQUE | Логин, хранится в нижнем регистре |
| `password_hash` | TEXT | bcrypt-хеш пароля |
| `created_at` | TIMESTAMPTZ | Дата регистрации |

Операции: создание (регистрация), чтение (`GET /api/me`), удаление (`DELETE /api/me`, каскадно удаляет ссылки и переходы).

### Link — короткая ссылка

| Поле | Тип | Описание |
|---|---|---|
| `id` | BIGSERIAL | Идентификатор |
| `user_id` | BIGINT, FK → users | Владелец |
| `code` | TEXT, UNIQUE | Короткий код или алиас |
| `url` | TEXT | Исходный адрес |
| `title` | TEXT | Название для пользователя |
| `enabled` | BOOLEAN | Включена ли ссылка |
| `expires_at` | TIMESTAMPTZ, NULL | Срок действия |
| `created_at` | TIMESTAMPTZ | Дата создания |

Полный CRUD:

| Операция | Запрос |
|---|---|
| Create | `POST /api/links` |
| Read | `GET /api/links`, `GET /api/links/{id}` |
| Update | `PUT /api/links/{id}` |
| Delete | `DELETE /api/links/{id}` |

Пользователь видит и изменяет только свои ссылки: каждый запрос фильтруется по `user_id` из JWT.

### Click — переход по ссылке

| Поле | Тип | Описание |
|---|---|---|
| `id` | BIGSERIAL | Идентификатор |
| `link_id` | BIGINT, FK → links | Ссылка |
| `referrer` | TEXT | Домен, с которого пришёл посетитель |
| `device` | TEXT | `desktop`, `mobile`, `tablet` или `bot` (по User-Agent) |
| `clicked_at` | TIMESTAMPTZ | Время перехода |

Создаётся при каждом успешном редиректе `GET /{code}`, читается через `GET /api/links/{id}/stats`, удаляется каскадно вместе со ссылкой.

## 4. Соответствие 12 факторам

### I. Кодовая база — одна кодовая база в системе контроля версий, много развёртываний

Весь код (бэкенд, фронтенд, миграции, Dockerfile'ы, `docker-compose.yml`) лежит в одном git-репозитории. Одна и та же кодовая база разворачивается в разных окружениях (локально, на стенде, в продакшене), отличается только конфигурация в переменных окружения. Разные сервисы (`api`, `web`, `migrate`) — это части одного приложения, а не отдельные приложения с общим кодом.

### II. Зависимости — явно объявляйте и изолируйте

- Go-зависимости объявлены в `api/go.mod`, их точные версии и контрольные суммы зафиксированы в `api/go.sum`.
- Бинарник собирается статически (`CGO_ENABLED=0`) и не зависит от системных библиотек.
- Системное окружение изолировано Docker-образами с зафиксированными версиями: `golang:1.27-alpine`, `alpine:3.22`, `postgres:17-alpine`, `nginx:1.29-alpine`.
- Приложение не рассчитывает на установленные на хосте утилиты: даже `wget` для healthcheck входит в базовый образ alpine.
- Фронтенд не имеет пакетных зависимостей. Единственный внешний ресурс — шрифты Google Fonts; без них страница остаётся работоспособной на системных шрифтах.

### III. Конфигурация — храните конфигурацию в окружении

Всё, что меняется между развёртываниями, читается из переменных окружения (`api/config.go`): `DATABASE_URL`, `JWT_SECRET`, `TOKEN_TTL`, `COOKIE_SECURE`, `BASE_URL`, `PORT`. Для nginx адрес бэкенда и порт тоже передаются через окружение (`API_ADDR`, `PORT`) и подставляются в шаблон конфигурации при старте контейнера.

В репозитории нет секретов: `.env` добавлен в `.gitignore`, в репозиторий попадает только пример `.env.example`. Критичные значения проверяются при старте: без `DATABASE_URL` или с `JWT_SECRET` короче 32 символов процесс завершается с понятной ошибкой, а `docker compose` не стартует без `JWT_SECRET`.

Проверка по тесту из методологии: репозиторий можно опубликовать прямо сейчас, не раскрыв ни одного секрета.

### IV. Сторонние службы — считайте их подключаемыми ресурсами

PostgreSQL подключается по URL из `DATABASE_URL`, и код не различает локальную и удалённую базу. Чтобы переключиться на управляемую БД (например, Yandex Managed PostgreSQL), достаточно поменять переменную окружения, код менять не нужно.

Бэкенд для nginx — тоже подключаемый ресурс, его адрес задаётся переменной `API_ADDR`.

### V. Сборка, релиз, выполнение — строго разделяйте этапы

- **Сборка**: `docker compose build` (или `docker build`) компилирует Go-бинарник в многоэтапном Dockerfile и упаковывает статику фронтенда в образ nginx. Результат — неизменяемые образы.
- **Релиз**: образ плюс конфигурация из окружения (`.env` / переменные в оркестраторе). Одна и та же сборка используется с разными конфигурациями.
- **Выполнение**: `docker compose up` запускает готовые образы. Во время выполнения код не меняется и не пересобирается.

Миграции схемы встроены в бинарник (`go:embed`) и тоже входят в релиз, поэтому версия схемы всегда соответствует версии кода.

### VI. Процессы — запускайте приложение как один или несколько процессов без состояния

Процесс `api` ничего не хранит между запросами:

- сессия — это подписанный JWT в cookie, который проверяется по `JWT_SECRET`, поэтому любой экземпляр `api` может обслужить любой запрос (не нужны sticky sessions);
- все данные (пользователи, ссылки, переходы) лежат в PostgreSQL;
- QR-коды генерируются на лету и не сохраняются на диск;
- локальная файловая система не используется.

### VII. Привязка портов — экспортируйте сервисы через привязку портов

`api` — самодостаточный HTTP-сервер на стандартном `net/http`, он сам слушает порт из переменной `PORT` и не требует внешнего сервера приложений. `web` (nginx) тоже слушает порт из `PORT`. Наружу публикуется только порт `web`, `api` доступен ему по внутренней сети Docker, и при необходимости `api` может выступать бэкенд-сервисом для других приложений.

### VIII. Параллелизм — масштабируйте приложение с помощью процессов

Нагрузка разделена по типам процессов: `web` (статика и прокси), `api` (бизнес-логика), `migrate` (разовые задачи). Каждый тип масштабируется независимо, горизонтально:

```bash
docker compose up -d --scale api=3
docker compose restart web
```

Это работает, потому что `api` не хранит состояние (фактор VI) и не публикует порт на хост, так что реплики не конфликтуют за порт. При старте nginx резолвит имя `api` во все адреса реплик и распределяет запросы между ними по round-robin, поэтому после изменения числа реплик `web` перезапускается. Внутри процесса параллелизм обеспечивает сам Go: каждый запрос обрабатывается в отдельной горутине, соединения с БД берутся из пула.

### IX. Утилизируемость — быстрый запуск и корректное завершение

- **Быстрый запуск**: статический бинарник стартует меньше чем за секунду, образ `api` весит около 29 МБ (8 МБ в сжатом виде).
- **Корректное завершение**: по `SIGTERM`/`SIGINT` сервер перестаёт принимать новые соединения, дожидается завершения текущих запросов (`http.Server.Shutdown` с таймаутом 10 секунд) и закрывает пул соединений с БД.
- **Устойчивость к падениям**: миграции выполняются в транзакциях, поэтому прерванная миграция не оставит схему в промежуточном состоянии. Каждый запрос к API атомарен, а у сервисов стоит `restart: unless-stopped`.
- **Healthcheck**: `GET /healthz` проверяет доступность БД. Compose запускает `web` только после того, как `api` стал healthy.

### X. Паритет разработки и эксплуатации — окружения должны быть максимально похожи

- Локально используются те же Docker-образы и тот же PostgreSQL 17, что и в эксплуатации, а не SQLite или in-memory заглушки.
- Одинаковый `docker-compose.yml` для всех окружений, различия только в `.env`.
- Код, написанный разработчиком, попадает в эксплуатацию без ручных шагов: собрать образ → запустить с нужным окружением.

### XI. Журналирование — рассматривайте логи как поток событий

Приложение пишет логи в `stdout` в структурированном JSON-формате (`log/slog`): каждый HTTP-запрос с методом, путём, статусом и длительностью, а также ошибки и события жизненного цикла (старт, остановка, применённые миграции). Приложение не управляет файлами логов и их ротацией. Сбором, хранением и маршрутизацией занимается окружение (`docker compose logs`, а в продакшене — Loki, ELK и т.п.). nginx по умолчанию тоже пишет access/error-логи в stdout/stderr контейнера.

```json
{"time":"2026-09-27T10:26:01.498Z","level":"INFO","msg":"request","method":"GET","path":"/api/links","status":200,"duration_ms":2}
```

### XII. Задачи администрирования — запускайте как разовые процессы

Миграции БД — это отдельная команда того же бинарника (`shorty migrate`), а не побочный эффект старта сервера. Она запускается разовым процессом `migrate` в `docker-compose.yml`:

- из того же образа, что и `api`, то есть с тем же кодом и теми же зависимостями;
- с той же конфигурацией (общий блок переменных `x-api-env`);
- до старта `api` (`depends_on: condition: service_completed_successfully`).

Вручную её можно запустить так:

```bash
docker compose run --rm migrate
```

Разовый запуск идемпотентен: применённые миграции записываются в таблицу `schema_migrations` и повторно не выполняются.
