# Отчёт: запуск shorty в Kubernetes (minikube)

**shorty** — сервис коротких ссылок: Go-бэкенд (`api`), фронтенд на nginx (`web`) и PostgreSQL. Ниже описано, как приложение развёрнуто в однонодовом кластере minikube.

## 1. Состав архива

```
Отчёт.md                  этот отчёт
k8s/
  kustomization.yaml      точка входа: kubectl apply -k k8s/
  namespace.yaml          Namespace shorty
  config.env              несекретная конфигурация → ConfigMap
  secret.env.example      шаблон секретов → Secret (копируется в secret.env)
  postgres.yaml           StatefulSet + headless Service для PostgreSQL
  migrate.yaml            Job с миграциями схемы БД
  api.yaml                Deployment + Service для Go-бэкенда
  web.yaml                Deployment + Service (NodePort) для фронтенда
api/                      исходный код бэкенда и его Dockerfile
web/                      фронтенд, конфиг nginx и Dockerfile
```

## 2. Сборка образов и запуск

```bash
minikube start

eval $(minikube docker-env)                 # docker теперь собирает прямо в minikube
docker build -t shorty-api:dev ./api
docker build -t shorty-web:dev ./web
minikube image load shorty-api:dev          # нужно, если образ собран в docker хоста
minikube image load shorty-web:dev

cp k8s/secret.env.example k8s/secret.env    # поменять пароль и JWT_SECRET
kubectl apply -k k8s/
kubectl get pods -n shorty -w

kubectl port-forward -n shorty svc/web 8080:80
# открыть http://localhost:8080
```

Первого администратора можно назначить разовой командой в работающем поде:

```bash
kubectl -n shorty exec deploy/api -- shorty promote you@example.com
```

Масштабирование:

```bash
kubectl -n shorty scale deployment/api --replicas=4
kubectl -n shorty scale deployment/web --replicas=3
kubectl -n shorty get pods -o wide
```

## 3. Использованные абстракции Kubernetes

### Namespace

`shorty` — все ресурсы приложения живут в отдельном пространстве имён. Их можно смотреть одной командой (`kubectl get all -n shorty`) и удалить одной командой (`kubectl delete namespace shorty`), не задевая остальное в кластере.

### ConfigMap и Secret

Конфигурация отделена от образов (фактор III из 12-factor). Одни и те же образы запускаются с любой конфигурацией.

| Объект | Откуда берётся | Что внутри |
|---|---|---|
| ConfigMap `shorty-config` | `config.env` | `POSTGRES_USER`, `POSTGRES_DB`, `BASE_URL`, `TOKEN_TTL`, `COOKIE_SECURE` |
| Secret `shorty-secret` | `secret.env` (не хранится в git) | `POSTGRES_PASSWORD`, `JWT_SECRET` |

Оба объекта создаются генераторами kustomize (`configMapGenerator`, `secretGenerator`). Генератор добавляет к имени хеш содержимого (`shorty-config-84bth9hkgf`) и сам подставляет это имя во все манифесты. При изменении конфигурации меняется имя, а значит и шаблон пода, поэтому Deployment сам перекатывает поды на новую конфигурацию. Без хеша пришлось бы делать `kubectl rollout restart` вручную.

Контейнеры получают значения через `envFrom`. `DATABASE_URL` не хранится отдельно, а собирается прямо в манифесте из уже объявленных переменных (подстановка `$(VAR)` в Kubernetes):

```yaml
- name: DATABASE_URL
  value: postgres://$(POSTGRES_USER):$(POSTGRES_PASSWORD)@postgres:5432/$(POSTGRES_DB)?sslmode=disable
```

Так пароль хранится в одном месте (Secret), и PostgreSQL с приложением не могут разойтись.

### StatefulSet + PersistentVolumeClaim — PostgreSQL

База запущена как **StatefulSet**, а не Deployment, потому что у неё есть состояние:

- у пода стабильное имя `postgres-0`, оно не меняется при пересоздании;
- `volumeClaimTemplates` создаёт для пода свой **PersistentVolumeClaim** `data-postgres-0` (1 Gi). В minikube его обслуживает StorageClass `standard`, который создаёт том на узле. Данные переживают удаление и перезапуск пода;
- при пересоздании под получает **тот же** том, а не новый пустой.

Реплика одна: PostgreSQL нельзя масштабировать простым увеличением `replicas`, для этого нужна репликация на уровне самой СУБД. Это нормальное ограничение для учебного стенда.

Проверки состояния:
- `readinessProbe` (`pg_isready`): пока база не готова принимать соединения, под не попадает в DNS-ответ Service;
- `livenessProbe` (`pg_isready`): если база зависла, kubelet перезапустит контейнер.

### Headless Service — `postgres`

```yaml
spec:
  clusterIP: None
```

У headless Service нет виртуального IP: DNS-имя `postgres` резолвится напрямую в IP пода `postgres-0`. Для базы с одной репликой балансировка не нужна, а StatefulSet требует такой Service (`serviceName: postgres`), чтобы у подов были стабильные DNS-имена.

### Job — миграции

Миграции схемы — это разовая административная задача (фактор XII), а не часть веб-сервера. Поэтому они запускаются отдельным **Job** `migrate`:

- образ тот же, что у `api` (`shorty-api:dev`), но с аргументом `migrate`, то есть код и зависимости гарантированно совпадают;
- **initContainer** `wait-for-postgres` (образ `postgres:17-alpine`, где есть `pg_isready`) ждёт, пока база начнёт принимать соединения. Без него Job падал бы при одновременном старте с базой;
- `restartPolicy: OnFailure` и `backoffLimit: 4`: при ошибке Job повторит попытку, но не бесконечно;
- после успеха под остаётся в статусе `Completed`, а его логи показывают применённые миграции.

Миграции идемпотентны (таблица `schema_migrations`), поэтому Job можно перезапустить в любой момент. Шаблон Job неизменяем, поэтому при выпуске новой версии образа Job нужно сначала удалить: `kubectl -n shorty delete job migrate && kubectl apply -k k8s/`.

### Deployment — `api` и `web`

Оба сервиса без состояния, поэтому запущены как **Deployment** по 2 реплики. Deployment управляет **ReplicaSet**, а тот — **Pod**'ами: поддерживает нужное число реплик, при обновлении образа или конфигурации делает rolling update без простоя.

| | `api` | `web` |
|---|---|---|
| Образ | `shorty-api:dev` | `shorty-web:dev` |
| Порт | 8080 | 80 |
| readinessProbe | `GET /healthz` (проверяет и соединение с БД) | `GET /` |
| livenessProbe | TCP-соединение с портом 8080 | `GET /` |
| requests / limits | 50m CPU, 32 Mi / 128 Mi | 25m CPU, 16 Mi / 64 Mi |

Почему пробы у `api` разные:
- **readiness** проверяет базу: если PostgreSQL недоступен, под временно убирается из балансировки, и запросы туда не идут;
- **liveness** только проверяет, что процесс отвечает. Если бы она тоже смотрела на базу, падение PostgreSQL перезапускало бы все поды `api` по кругу, хотя проблема не в них.

`imagePullPolicy: IfNotPresent`: образы загружены в minikube локально (`minikube image load` или сборка через `docker-env`), и Kubernetes не пытается скачать их из реестра.

`securityContext` у `api`: процесс работает от непривилегированного пользователя (UID 10001 задан в Dockerfile), с `readOnlyRootFilesystem` и без повышения привилегий. Go-сервер ничего не пишет на диск, поэтому файловая система только для чтения ему не мешает.

`terminationGracePeriodSeconds: 15`: при остановке пода Kubernetes шлёт SIGTERM, и сервер завершает текущие запросы (`http.Server.Shutdown`), прежде чем выйти.

### Service ClusterIP — `api`

Внутренний Service с постоянным виртуальным IP и DNS-именем `api`. kube-proxy распределяет соединения на этот IP между всеми **готовыми** подами `api` (с пройденной readinessProbe). Снаружи кластера он недоступен.

### Service NodePort — `web`

Единственная точка входа снаружи: порт `30080` на узле minikube. Открыть сайт можно тремя способами:

- `kubectl port-forward -n shorty svc/web 8080:80` → `http://localhost:8080` (совпадает с `BASE_URL` по умолчанию);
- `minikube service web -n shorty` — minikube сам откроет нужный адрес;
- `http://$(minikube ip):30080` — на Linux с драйвером docker.

Если сайт открывается не по `localhost:8080`, нужно поменять `BASE_URL` в `config.env` и снова выполнить `kubectl apply -k k8s/`. Из `BASE_URL` строятся короткие ссылки и QR-коды, а поды перекатятся сами благодаря хешу в имени ConfigMap.

### Kustomize

`kustomization.yaml` собирает всё вместе. Он встроен в `kubectl`, ставить ничего не нужно (`kubectl apply -k`), и делает следующее:
- проставляет namespace `shorty` всем ресурсам;
- генерирует ConfigMap и Secret из `.env`-файлов;
- задаёт теги образов в одном месте (`images: newTag: dev`). Чтобы выпустить новую версию, достаточно поменять тег здесь;
- добавляет общую метку `app.kubernetes.io/part-of: shorty`.

## 4. Как сервисы взаимодействуют между собой

```
                    ┌───────────── кластер minikube, namespace shorty ─────────────┐
                    │                                                              │
 браузер ──► NodePort 30080 / port-forward                                         │
                    │                                                              │
                    ▼                                                              │
              Service web ──► Pod web ×2 (nginx)                                   │
                    │            │  /, /assets/*  → статика из образа              │
                    │            │  /api/*, /{code}, /healthz                      │
                    │            ▼                                                 │
                    │      Service api (ClusterIP) ──► Pod api ×2..N (Go)          │
                    │                                     │                        │
                    │                                     ▼                        │
                    │      Service postgres (headless) ──► Pod postgres-0 ──► PVC  │
                    │                                     ▲                        │
                    │      Job migrate ───────────────────┘ (один раз при запуске) │
                    └──────────────────────────────────────────────────────────────┘
```

### Браузер → web

Пользователь заходит на NodePort `web` (или через port-forward). Service `web` направляет запрос в один из подов nginx.

### web → api

nginx отдаёт статику (HTML, CSS, JS, шрифты) сам, а всё остальное проксирует на адрес из переменной окружения `API_ADDR=api:8080`:

```nginx
location / { proxy_pass http://api:8080; }
```

Имя `api` — это DNS-имя Service (полностью `api.shorty.svc.cluster.local`), его резолвит CoreDNS кластера. nginx получает **один** ClusterIP Service, а распределение по подам делает kube-proxy. Поэтому при `kubectl scale deployment/api --replicas=4` новые поды начинают получать запросы сразу после прохождения readinessProbe: nginx не нужно ни перезапускать, ни перенастраивать. В docker compose для этого приходилось перезапускать `web`, потому что nginx там резолвил имя прямо в адреса контейнеров.

nginx открывает к upstream новое соединение на каждый запрос, а kube-proxy выбирает под для каждого соединения. В итоге запросы расходятся по репликам примерно поровну. Это видно в логах:

```bash
kubectl -n shorty logs -l app=api --prefix --tail=5
```

### api → postgres

`api` подключается к базе по `DATABASE_URL`, где хост — `postgres`. Headless Service резолвит это имя прямо в IP пода `postgres-0`. Все реплики `api` работают с одной базой через пул соединений (`pgxpool`).

### Почему api можно масштабировать

Процессы `api` не хранят состояние (фактор VI):
- сессия пользователя — это JWT в cookie, подписанный `JWT_SECRET` из общего Secret. Токен, выданный одной репликой, принимает любая другая, sticky sessions не нужны;
- все данные лежат в PostgreSQL;
- статус бана и права администратора проверяются в базе на каждом запросе, поэтому бан сразу действует на всех репликах.

### Job migrate → postgres

При `kubectl apply -k` Job стартует одновременно с базой. Его initContainer ждёт готовности PostgreSQL, после чего `shorty migrate` создаёт таблицы и завершается. Поды `api` в это время уже могут работать: их readinessProbe проверяет только соединение с базой. Первые секунды после самого первого запуска запросы к ещё не созданным таблицам могут вернуть ошибку, но к моменту, когда открывается браузер, миграции уже применены (обычно Job выполняется за 10–20 секунд).

### Конфигурация

ConfigMap и Secret подключены через `envFrom` ко всем, кому они нужны:

| Под | ConfigMap | Secret | Свои переменные |
|---|---|---|---|
| `postgres-0` | `POSTGRES_USER`, `POSTGRES_DB` | `POSTGRES_PASSWORD` | `PGDATA` |
| `migrate` | ✓ | ✓ | `DATABASE_URL` |
| `api` | ✓ | ✓ | `PORT`, `DATABASE_URL` |
| `web` | — | — | `PORT`, `API_ADDR` |

## 5. Что важно знать при работе

- **`kubectl apply -k` возвращает число реплик к значению из манифеста** (2). После ручного `kubectl scale` повторный apply снова уменьшит число подов. Для постоянного изменения нужно поменять `replicas` в `api.yaml` / `web.yaml`.
- **Данные PostgreSQL** лежат в PVC и переживают удаление пода (`kubectl delete pod postgres-0`). Удаляются они только вместе с PVC или namespace.
- **Логи** всех сервисов пишутся в stdout (JSON у `api`), их собирает Kubernetes: `kubectl logs -n shorty deploy/api`, `kubectl logs -n shorty job/migrate`.
- **Удалить всё:** `kubectl delete -k k8s/`. PVC при этом удалится вместе с namespace.
