# Отчёт: запуск shorty в Kubernetes (minikube)

**shorty** — сервис коротких ссылок из трёх частей: Go-бэкенд (`api`), фронтенд на nginx (`web`) и база PostgreSQL. Архив содержит исходный код, Dockerfile'ы обоих сервисов, манифесты и скрипт `run.sh` с полным сценарием запуска.

## 1. Файлы

| Файл | Что внутри |
|---|---|
| `api/Dockerfile` | сборка образа бэкенда `shorty-api` |
| `web/Dockerfile` | сборка образа фронтенда `shorty-web` |
| `run.sh` | полный сценарий: minikube, ingress, сборка, загрузка образов, деплой, ожидание готовности |
| `k8s/00-namespace.yaml` | Namespace `shorty` |
| `k8s/10-config.yaml` | ConfigMap `app-config` |
| `k8s/11-secrets.yaml` | Secret `db-secret` и Secret `app-secret` |
| `k8s/20-postgres.yaml` | headless Service + StatefulSet для PostgreSQL |
| `k8s/30-migrate.yaml` | Job `migrate`, создаёт таблицы |
| `k8s/40-api.yaml` | Deployment + Service для бэкенда |
| `k8s/50-web.yaml` | Deployment + Service для фронтенда |
| `k8s/60-ingress.yaml` | Ingress `shorty.localhost` → `web` |

Номера в именах файлов задают порядок: `kubectl apply -f k8s/` применяет файлы по алфавиту, поэтому Namespace создаётся раньше всего, что в нём живёт.

## 2. Образы

### `shorty-api` — `api/Dockerfile`

```dockerfile
FROM golang:1.27-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /shorty .

FROM alpine:3.22
RUN adduser -D -H -u 10001 app
USER 10001
COPY --from=build /shorty /usr/local/bin/shorty
EXPOSE 8080
ENTRYPOINT ["shorty"]
CMD ["serve"]
```

Многоэтапная сборка:
- **Первый этап** (`golang:1.27-alpine`) компилирует статический бинарник. Зависимости (`go.mod`, `go.sum`) копируются и скачиваются отдельным слоем, поэтому при изменении только кода они берутся из кэша.
- **Второй этап** (`alpine:3.22`) содержит только бинарник и запускает его от непривилегированного пользователя с UID 10001. Итоговый образ весит около 30 МБ вместо 300+ МБ с компилятором.

Один и тот же образ выполняет три команды: `serve` (веб-сервер, по умолчанию), `migrate` (миграции БД, их запускает Job) и `promote <email>` (выдать права администратора).

### `shorty-web` — `web/Dockerfile`

```dockerfile
FROM nginx:1.29-alpine
COPY nginx.conf.template /etc/nginx/templates/default.conf.template
COPY public /usr/share/nginx/html
```

Внутри nginx со статикой фронтенда (HTML, CSS, JS, шрифты). Конфиг — шаблон: при старте контейнера официальный образ nginx подставляет в него переменные окружения `PORT` и `API_ADDR`. Так адрес бэкенда задаётся в манифесте, а не зашит в образ.

## 3. Как собрать образы

```bash
minikube start --driver=docker
eval $(minikube docker-env)

docker build -t shorty-api:dev ./api
docker build -t shorty-web:dev ./web

minikube image load shorty-api:dev
minikube image load shorty-web:dev
```

`eval $(minikube docker-env)` переключает `docker` в текущем терминале на Docker-демон внутри minikube, поэтому `docker build` складывает образы сразу туда, где их будет искать Kubernetes. `minikube image load` — второй способ доставить образ в кластер: он нужен, если образ собран обычным Docker на хосте. После `docker-env` эта команда ничего не меняет, но и не мешает.

В манифестах у образов приложения стоит `imagePullPolicy: Never`. Kubernetes не пытается скачать `shorty-api:dev` из Docker Hub (там его нет), а берёт только локальный образ. Если образ забыли собрать, под сразу покажет понятную ошибку `ErrImageNeverPull`, а не будет долго пытаться скачать несуществующий образ.

## 4. Как запустить

Весь сценарий одной командой:

```bash
./run.sh
```

Или по шагам:

```bash
minikube start --driver=docker
minikube addons enable ingress

eval $(minikube docker-env)
docker build -t shorty-api:dev ./api
docker build -t shorty-web:dev ./web
minikube image load shorty-api:dev
minikube image load shorty-web:dev

kubectl delete job migrate -n shorty --ignore-not-found
kubectl apply -f k8s/

kubectl -n shorty rollout status statefulset/postgres
kubectl -n shorty wait --for=condition=complete job/migrate
kubectl -n shorty rollout status deployment/api
kubectl -n shorty rollout status deployment/web
kubectl -n shorty get pods,svc,ingress
```

В отдельном терминале открыть доступ к Ingress-контроллеру:

```bash
kubectl -n ingress-nginx port-forward svc/ingress-nginx-controller 8080:80
```

После этого приложение открывается по адресу **http://shorty.localhost:8080**. Браузеры и curl сами направляют любые `*.localhost` на `127.0.0.1`, поэтому файл `hosts` править не нужно.

Почему port-forward идёт именно на Ingress-контроллер. minikube работает в WSL с драйвером docker, и порт контроллера внутри minikube недоступен из браузера Windows. `minikube tunnel` выводит Ingress на `127.0.0.1` только на macOS и Windows, а WSL для minikube — это Linux. Проброс порта контроллера решает эту проблему, и при этом запросы по-прежнему проходят через Ingress и его правило по хосту: сайт по другому имени не откроется. В настоящем кластере у контроллера был бы внешний IP (Service типа LoadBalancer), и проброс был бы не нужен.

Сделать пользователя администратором:

```bash
kubectl -n shorty exec deploy/api -- shorty promote you@example.com
```

## 5. Порядок запуска

```
Namespace, ConfigMap, Secret
        │
        ▼
StatefulSet postgres ──readinessProbe pg_isready──► Ready
        │
        ▼
Job migrate: initContainer ждёт pg_isready → migrate создаёт таблицы → Completed
        │
        ▼
Deployment api: readinessProbe GET /healthz (проверяет соединение с БД) → Ready
        │
        ▼
Deployment web: readinessProbe GET / → Ready ──► Ingress начинает отдавать сайт
```

Все объекты создаются одной командой `kubectl apply`, а порядок обеспечивают проверки:
- **Job `migrate`** не стартует, пока его initContainer `wait-for-postgres` не дождётся ответа `pg_isready` от базы. Раньше Job стартовал одновременно с базой, падал и перезапускался, то есть работал «случайно». Теперь он запускается один раз и сразу успешно, без рестартов.
- **Поды `api`** не получают трафик, пока `/healthz` не подтвердит соединение с базой.
- **Поды `web`** не получают трафик, пока nginx не начнёт отвечать.

## 6. Как масштабировать

```bash
kubectl -n shorty scale deployment/api --replicas=4
kubectl -n shorty scale deployment/web --replicas=3
kubectl -n shorty get rs,pods
```

`kubectl scale` меняет поле `replicas` у Deployment. Deployment передаёт число своему ReplicaSet, а ReplicaSet создаёт недостающие Pod'ы (или удаляет лишние). Новые поды попадают в балансировку Service, как только проходят readinessProbe.

**Почему масштабируются `api` и `web`.** Они stateless: не хранят ничего у себя, поэтому любой запрос может обработать любая реплика.
- `web` — это nginx со статикой и проксированием, у него нет состояния вообще.
- `api` хранит данные в PostgreSQL, а сессия пользователя — это JWT-токен в cookie, подписанный `JWT_SECRET` из общего Secret. Токен, выданный одной репликой, проверит любая другая.

**Почему `postgres` остаётся в одной реплике.** У базы есть состояние — данные на диске. Вторая реплика с `scale` не стала бы копией первой: это был бы второй независимый сервер со своим пустым диском. Для нескольких реплик PostgreSQL нужна репликация на уровне самой СУБД (primary/replica, например через оператор), а это за рамками задания.

## 7. Использованные абстракции Kubernetes

### Namespace — `shorty`

Все объекты приложения живут в отдельном пространстве имён, а не в `default`. Их можно посмотреть одной командой (`kubectl -n shorty get all`) и не путать с чужими. На все объекты повешены общие метки `app.kubernetes.io/name`, `app.kubernetes.io/component`, `app.kubernetes.io/part-of: shorty`. Селекторы Service и Deployment используют `app.kubernetes.io/name`.

### Pod

Минимальная единица запуска: один или несколько контейнеров с общей сетью. Поды напрямую не создаются: их создают ReplicaSet (для Deployment), StatefulSet и Job. Если под упал, его владелец создаст новый.

### ReplicaSet

Следит, чтобы подов с нужными метками было ровно `replicas` штук. Именно его число меняется при масштабировании. Создаётся автоматически Deployment'ом: на каждую версию шаблона пода — свой ReplicaSet. При обновлении образа Deployment плавно уменьшает старый ReplicaSet и увеличивает новый (rolling update), и сайт не простаивает.

### Deployment — `api`, `web`

Описывает stateless-сервис: образ, переменные, пробы, ресурсы и число реплик. Управляет ReplicaSet'ами.

| Deployment | Образ | Реплик | Порт | readinessProbe | livenessProbe |
|---|---|---|---|---|---|
| `api` | `shorty-api:dev` | 2 | 8080 | `GET /healthz` | TCP-порт 8080 |
| `web` | `shorty-web:dev` | 2 | 80 | `GET /` | `GET /` |

### StatefulSet + PersistentVolumeClaim — `postgres`

База данных запущена как **StatefulSet**, это стандартный объект для сервисов с состоянием:
- у пода стабильное имя `postgres-0`, оно не меняется при пересоздании;
- `volumeClaimTemplates` создаёт для пода свой **PersistentVolumeClaim** `data-postgres-0` (1 Gi). minikube выделяет под него том на узле. При пересоздании под получает тот же диск, поэтому данные переживают перезапуск;
- StatefulSet никогда не запускает два пода `postgres-0` одновременно: новый стартует только после остановки старого. В прошлой версии с Deployment для этого была нужна стратегия `Recreate` (иначе при обновлении на время rolling update оказалось бы два PostgreSQL на одном томе). StatefulSet гарантирует это сам.

PVC из `volumeClaimTemplates` не удаляется вместе со StatefulSet. Проверено: после `kubectl -n shorty delete statefulset postgres` и повторного `apply` все пользователи и ссылки на месте.

### Job — `migrate`

Под, который должен один раз выполниться и завершиться. Запускает тот же образ, что `api`, с аргументом `migrate`: программа применяет SQL-миграции и выходит. Миграции идемпотентны (таблица `schema_migrations`), повторный запуск ничего не ломает.

| Поле | Зачем |
|---|---|
| `initContainers: wait-for-postgres` | ждёт, пока `pg_isready` ответит, и только потом запускает миграцию |
| `restartPolicy: OnFailure` | если миграция всё-таки упала (например, база перезапустилась), повторить её в том же поде |
| `backoffLimit: 3` | не повторять бесконечно: после трёх неудач Job помечается как Failed |
| `ttlSecondsAfterFinished: 600` | через 10 минут после завершения Job удаляется сам |

Шаблон пода в Job неизменяем, и повторный `kubectl apply` с новым образом завершился бы ошибкой. Поэтому `run.sh` перед `apply` удаляет старый Job (`kubectl delete job migrate --ignore-not-found`), и миграции применяются при каждом деплое. Если деплоя не было больше 10 минут, Job к этому моменту уже удалён по `ttlSecondsAfterFinished`.

### Service

Даёт группе подов постоянное DNS-имя и адрес и распределяет между ними запросы. Нужен потому, что IP-адреса подов меняются при каждом пересоздании.

| Service | Тип | Кто к нему ходит |
|---|---|---|
| `postgres` | headless (`clusterIP: None`) | `api`, `migrate` |
| `api` | ClusterIP | `web` |
| `web` | ClusterIP | Ingress |

**Headless Service** у базы не балансирует, а резолвит имя `postgres` прямо в IP пода `postgres-0`. Такой Service требует StatefulSet (`serviceName: postgres`), и для одной реплики балансировка не нужна.

Все Service'ы — внутренние (ClusterIP). Снаружи кластер доступен только через Ingress.

### Ingress — `shorty`

Правило «запросы на хост `shorty.localhost` отправлять в Service `web`, порт 80». Его выполняет Ingress-контроллер nginx, который включается аддоном `minikube addons enable ingress` (`ingressClassName: nginx`).

Благодаря Ingress у приложения постоянный адрес `http://shorty.localhost:8080`, а `web` больше не нужно выставлять наружу через NodePort или пробрасывать к нему порт. Этот же адрес записан в `BASE_URL`, поэтому короткие ссылки и QR-коды, которые генерирует `api`, ведут туда, где приложение реально открывается. Раньше Service `web` был типа NodePort (30080), а в демонстрации использовался `port-forward` на 8080. Теперь способ доступа один.

### ConfigMap — `app-config`

Обычные (не секретные) настройки: `BASE_URL`, `TOKEN_TTL`, `COOKIE_SECURE`. Подключаются в `api` и `migrate` через `envFrom`: каждый ключ ConfigMap становится переменной окружения с тем же именем. `envFrom` удобен, когда контейнеру нужны все ключи объекта: не нужно перечислять каждую переменную по отдельности.

### Secret — `db-secret` и `app-secret`

Секреты разделены по назначению, чтобы каждый контейнер получал только нужное:

| Secret | Ключи | Кто получает |
|---|---|---|
| `db-secret` | `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `postgres` целиком через `envFrom`. `api` и `migrate` — только три значения через `secretKeyRef` |
| `app-secret` | `JWT_SECRET` | `api` и `migrate` через `envFrom` |

`api` не получает `POSTGRES_*` как есть. Логин, пароль и имя базы берутся по отдельным ключам и собираются в `DATABASE_URL` прямо в манифесте с помощью подстановки `$(VAR)`:

```yaml
- name: DATABASE_URL
  value: postgres://$(DB_USER):$(DB_PASSWORD)@postgres:5432/$(DB_NAME)?sslmode=disable
```

Пароль хранится в одном месте, и база с приложением не могут разойтись.

### Ресурсы

У каждого контейнера заданы `requests` (сколько CPU и памяти планировщик резервирует под под) и `limits` (больше этого под не получит). Например, `api` запрашивает 50m CPU и 32 Mi и ограничен 250m CPU и 128 Mi. При масштабировании планировщик по `requests` проверяет, помещаются ли новые поды на узел. Без `requests` он считал бы их бесплатными и мог бы перегрузить узел.

## 8. Как сервисы взаимодействуют между собой

```
браузер ──http://shorty.localhost:8080──► port-forward ──► Ingress (nginx-контроллер)
                                                              │ host: shorty.localhost
                                                              ▼
                                         Service web ──► Pod web (nginx) ×2
                                                              │ /, /assets/* — отдаёт сам
                                                              │ /api/*, /{code}, /healthz
                                                              ▼
                                         Service api ──► Pod api (Go) ×2
                                                              │
                                                              ▼
                              Service postgres (headless) ──► Pod postgres-0 ──► PVC data-postgres-0
                                                              ▲
                                         Job migrate ─────────┘ (один раз при деплое)
```

- **Браузер → Ingress → web.** Ingress-контроллер по заголовку `Host: shorty.localhost` отправляет запрос в Service `web`, а тот — в один из подов nginx.
- **web → api.** nginx сам отдаёт статику, а запросы к API и короткие ссылки проксирует на `http://api:8080` (переменная `API_ADDR`). `api` — это DNS-имя Service внутри namespace. Service распределяет запросы между всеми готовыми подами `api`, поэтому после `scale` новые реплики сразу получают трафик без перенастройки nginx.
- **api → postgres.** `api` подключается к `postgres:5432` по `DATABASE_URL`. Все реплики работают с одной базой.
- **migrate → postgres.** Job подключается к той же базе, создаёт таблицы и завершается.

## 9. Ограничения и что важно знать

- **Секреты лежат в репозитории открытым текстом** (`11-secrets.yaml`, пароль `shorty` и учебный `JWT_SECRET`). Для учебного стенда это допустимо. В реальном окружении секреты не хранят в git: их создают командой `kubectl create secret` в CI или берут из хранилища (Vault, Sealed Secrets, External Secrets). Перед реальным запуском значения нужно поменять.
- **`kubectl delete -f k8s/` удаляет всё вместе с данными.** Команда удаляет Namespace `shorty`, а с ним и PVC базы. Для демонстрации это удобно, в рабочем окружении так делать нельзя. Чтобы остановить приложение и сохранить данные, удаляйте только рабочие нагрузки:
  ```bash
  kubectl -n shorty delete deployment,statefulset,job --all
  ```
  PVC `data-postgres-0` при этом останется, и после `kubectl apply -f k8s/` база поднимется с прежними данными.
- **`port-forward` к Ingress-контроллеру должен работать всё время**, пока нужен доступ к сайту. Без него Ingress внутри кластера работает, но из браузера недоступен.
