# Отчёт: запуск shorty в Kubernetes (minikube)

**shorty** — сервис коротких ссылок из трёх частей: Go-бэкенд (`api`), фронтенд на nginx (`web`) и база PostgreSQL.

## Файлы

| Файл | Что внутри |
|---|---|
| `k8s/config.yaml` | ConfigMap с обычными настройками |
| `k8s/secret.yaml` | Secret с паролями |
| `k8s/postgres.yaml` | PVC + Deployment + Service для базы |
| `k8s/migrate.yaml` | Job, который создаёт таблицы в базе |
| `k8s/api.yaml` | Deployment + Service для бэкенда |
| `k8s/web.yaml` | Deployment + Service для фронтенда |
| `api/Dockerfile`, `web/Dockerfile` | сборка образов |

## Запуск

```bash
minikube start

eval $(minikube docker-env)
docker build -t shorty-api:dev ./api
docker build -t shorty-web:dev ./web
minikube image load shorty-api:dev
minikube image load shorty-web:dev

kubectl apply -f k8s/
kubectl get pods

kubectl port-forward svc/web 8080:80
# открыть http://localhost:8080
```

Масштабирование:

```bash
kubectl scale deployment/api --replicas=4
kubectl scale deployment/web --replicas=3
kubectl get pods
```

Сделать пользователя админом:

```bash
kubectl exec deploy/api -- shorty promote you@example.com
```

Удалить всё:

```bash
kubectl delete -f k8s/
```

## Какие абстракции Kubernetes использованы

### Pod

Минимальная единица запуска: один или несколько контейнеров. Сами поды мы не создаём, их создают Deployment и Job.

### Deployment — `api`, `web`, `postgres`

Deployment говорит: «держи запущенными N одинаковых подов с таким-то образом». Если под упал, Deployment создаст новый. Команда `kubectl scale` просто меняет число N.

| Deployment | Образ | Реплик | Порт |
|---|---|---|---|
| `api` | `shorty-api:dev` | 2 | 8080 |
| `web` | `shorty-web:dev` | 2 | 80 |
| `postgres` | `postgres:17-alpine` | 1 | 5432 |

У `api` есть `readinessProbe`: Kubernetes каждые 10 секунд дёргает `GET /healthz`. Пока ответ не 200 (например, база ещё не поднялась), трафик в этот под не идёт.

У `postgres` реплика всегда одна: базу нельзя размножить простым `scale`. Стратегия `Recreate` означает, что при обновлении старый под останавливается до старта нового, и два PostgreSQL не пишут в один том одновременно.

### Job — `migrate`

Job — это под, который должен один раз выполниться и завершиться. Он запускает тот же образ, что и `api`, но с аргументом `migrate`: программа создаёт таблицы и выходит.

`restartPolicy: OnFailure`: если база ещё не готова, миграция падает и Kubernetes перезапускает её, пока не получится. Поэтому у пода `migrate` в `kubectl get pods` может быть 1–2 рестарта перед статусом `Completed`, и это нормально.

### Service — `api`, `web`, `postgres`

У подов меняются IP-адреса при каждом пересоздании. Service даёт постоянное имя и адрес, по которому можно достучаться до подов с нужной меткой (`selector: app: api`), и сам распределяет запросы между ними.

| Service | Тип | Кто к нему ходит |
|---|---|---|
| `postgres` | ClusterIP (только внутри кластера) | `api` и `migrate` |
| `api` | ClusterIP (только внутри кластера) | `web` |
| `web` | NodePort `30080` (доступен снаружи) | браузер |

### ConfigMap — `shorty-config`

Обычные настройки, которые не являются секретом: `BASE_URL`, `TOKEN_TTL`, `COOKIE_SECURE`. Контейнеры получают их как переменные окружения через `envFrom`.

### Secret — `shorty-secret`

То же, что ConfigMap, но для паролей: логин и пароль PostgreSQL, `DATABASE_URL`, `JWT_SECRET`. Его читают `postgres` (чтобы создать пользователя), `migrate` и `api` (чтобы подключиться).

В репозитории лежат учебные значения. Для настоящего запуска их нужно поменять в `secret.yaml`.

### PersistentVolumeClaim — `postgres-data`

Запрос на диск размером 1 Gi. minikube сам создаёт под него том. Диск подключается к поду `postgres`, поэтому данные переживают перезапуск и пересоздание пода.

## Как сервисы взаимодействуют между собой

```
браузер
   │  kubectl port-forward svc/web 8080:80  (или NodePort 30080)
   ▼
Service web ──► Pod web (nginx) ×2
                   │  отдаёт сам: /, /assets/*
                   │  проксирует: /api/*, /{code}, /healthz
                   ▼
Service api ──► Pod api (Go) ×2
                   │
                   ▼
Service postgres ──► Pod postgres ──► PVC postgres-data
                   ▲
Job migrate ───────┘  (один раз при запуске)
```

**Браузер → web.** Пользователь открывает сайт, Service `web` отправляет запрос в один из подов nginx.

**web → api.** nginx сам отдаёт HTML, CSS и JS, а запросы к API и короткие ссылки пересылает на `http://api:8080`. Адрес задан переменной `API_ADDR` в `web.yaml`. Имя `api` — это имя Service: DNS внутри кластера превращает его в адрес Service, а тот выбирает один из подов `api`. Поэтому после `kubectl scale deployment/api --replicas=4` запросы сразу начинают расходиться по четырём подам, и nginx ничего не нужно перенастраивать.

**api → postgres.** `api` подключается к базе по `DATABASE_URL` из Secret: `postgres://...@postgres:5432/shorty`. Здесь `postgres` — тоже имя Service. Все реплики `api` работают с одной базой.

**migrate → postgres.** При запуске Job подключается к той же базе по тому же `DATABASE_URL`, создаёт таблицы и завершается.

**Почему `api` можно масштабировать.** Поды `api` ничего не хранят у себя: данные лежат в PostgreSQL, а вход пользователя — это JWT-токен в cookie, подписанный `JWT_SECRET` из общего Secret. Токен, выданный одним подом, принимает любой другой, поэтому неважно, в какой под попадёт следующий запрос.
