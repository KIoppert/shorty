# Отчет: SLI, SLO и SLA для shorty

## Что добавлено

| Файл | Что внутри |
|---|---|
| `api/probe.go` | пробер: команда `shorty probe` того же образа, что и `api` |
| `api/faults.go` | управляемые сбои для демонстрации: задержка и доля ошибок 500 |
| `api/config.go` | переменные `FAULT_DELAY` и `FAULT_ERROR_RATE` |
| `k8s/70-prober.yaml` | Deployment `prober` с аннотациями `prometheus.io/*` |
| `k8s/slo/load.sh` | постоянная нагрузка на приложение, чтобы request-based SLI было из чего считать |

VictoriaMetrics, сбор по аннотациям и метрики `api` и `postgres-exporter` остались из прошлого задания. Пробер находится тем же service discovery: у его пода аннотации `prometheus.io/scrape: "true"` и `prometheus.io/port: "9091"`, поэтому настройку сбора менять не пришлось.

## Выбранные метрики

| Метрика | Откуда | Тип | Что показывает |
|---|---|---|---|
| `shorty_http_requests_total{route, method, status}` | `api` | counter | число запросов по маршруту и коду ответа |
| `shorty_http_request_duration_seconds_bucket{route, method, le}` | `api` | histogram | распределение времени ответа |
| `pg_up` | `postgres-exporter` | gauge | доступна ли база: 1 или 0 |
| `shorty_probe_total{check, result}` | `prober` | counter | проверки пробера по результату: `success`, `failure` |

Первые три метрики сделаны в прошлом задании, четвертую отдает пробер.

Запросы к `GET /healthz` исключены из всех SLI: их шлет Kubernetes каждые 5 секунд, они составляют большую часть трафика и не отражают опыт пользователя.

### Пробер

Пробер работает отдельным подом и каждые 10 секунд ходит в приложение как пользователь, через Service `web` (nginx), то есть по всей цепочке `web -> api -> PostgreSQL`:

| Проверка | Запрос | Успех |
|---|---|---|
| `web` | `GET /` | 200, фронтенд отдается |
| `health` | `GET /healthz` | 200, api отвечает и видит базу |
| `redirect` | `GET /prober-check` | 302, работает главная функция сервиса: переход по короткой ссылке |

Для проверки `redirect` пробер при первом запуске регистрирует служебного пользователя и создает ссылку `prober-check`. Если проверка не прошла, перед следующей попыткой он повторяет подготовку, поэтому переживает пересоздание базы.

Пробер нужен потому, что метрики `api` видят только запросы, которые до `api` дошли. Когда база недоступна, readiness-проба `/healthz` выводит поды `api` из Service, и nginx отвечает 502 сам. Счетчики `api` этих ошибок не видят, а пробер видит.

## SLI, SLO и SLA

Окно SLO и SLA: 30 дней. На скринкасте используется окно 30 минут, иначе изменения были бы не видны. В формулах окно обозначено `[W]`, на графиках `W = 30m`.

### SLI-1. Доступность API (request-based)

Доля запросов, на которые `api` ответил без ошибки сервера.

```
SLI-1 = успешные запросы / все запросы

sum(increase(shorty_http_requests_total{route!="GET /healthz",status!~"5.."}[W]))
  /
sum(increase(shorty_http_requests_total{route!="GET /healthz"}[W]))
```

Ответы 4xx считаются успешными: неверный пароль или несуществующая ссылка означают ошибку клиента, а не сервиса.

**SLO-1:** не меньше 99.5% запросов за 30 дней отвечают без 5xx. Бюджет ошибок: 0.5% запросов.

### SLI-2. Скорость ответа (request-based)

Доля запросов, обработанных быстрее 250 мс.

```
SLI-2 = быстрые запросы / все запросы

sum(increase(shorty_http_request_duration_seconds_bucket{route!="GET /healthz",le="0.25"}[W]))
  /
sum(increase(shorty_http_request_duration_seconds_count{route!="GET /healthz"}[W]))
```

Бакет `le="0.25"` гистограммы содержит число запросов не дольше 0.25 с, `_count` содержит число всех запросов.

**SLO-2:** не меньше 99% запросов за 30 дней обрабатываются быстрее 250 мс.

### SLI-3. Доступность базы (time-based)

Доля минут, когда PostgreSQL был доступен.

```
SLI-3 = минуты с pg_up = 1 / все минуты

avg_over_time((max(pg_up) or max(shorty_probe_success) * 0)[W:1m])
```

Подзапрос `[W:1m]` вычисляет выражение раз в минуту. Если под базы удален, вместе с ним пропадает и экспортер, и `pg_up` перестает приходить совсем. Часть `or max(shorty_probe_success) * 0` превращает такую минуту в 0, пока пробер работает. Без нее минуты простоя просто выпали бы из расчета.

**SLO-3:** база доступна не меньше 99.9% минут за 30 дней.

### SLI-4. Доступность для пользователя по данным пробера (request-based)

Доля успешных проверок пробера.

```
SLI-4 = успешные проверки / все проверки

sum(increase(shorty_probe_total{result="success"}[W]))
  /
sum(increase(shorty_probe_total[W]))
```

**SLO-4:** не меньше 99.5% проверок пробера за 30 дней успешны.

### Общий SLI: хорошие минуты (time-based)

Минута хорошая, если в ней выполнены все условия:

| Условие | Порог за минуту |
|---|---|
| ошибки 5xx | не больше 1% запросов |
| медленные запросы (дольше 250 мс) | не больше 5% запросов |
| база | `pg_up = 1` всю минуту |
| пробер | ни одной неудачной проверки |

```
SLI = хорошие минуты / все минуты
```

В MetricsQL условие записано через `WITH`, это шаблоны внутри запроса. `x <= bool 0.01` возвращает 1 или 0, произведение условий равно 1, только если выполнены все:

```
WITH (
  ok_errors = (sum(increase(shorty_http_requests_total{route!="GET /healthz",status=~"5.."}[1m])) or vector(0))
    / clamp_min(sum(increase(shorty_http_requests_total{route!="GET /healthz"}[1m])), 1) <= bool 0.01,
  ok_latency = (sum(increase(shorty_http_request_duration_seconds_count{route!="GET /healthz"}[1m]))
    - sum(increase(shorty_http_request_duration_seconds_bucket{route!="GET /healthz",le="0.25"}[1m])))
    / clamp_min(sum(increase(shorty_http_request_duration_seconds_count{route!="GET /healthz"}[1m])), 1) <= bool 0.05,
  ok_db = min(min_over_time(pg_up[1m])) == bool 1,
  ok_probes = sum(increase(shorty_probe_total{result="failure"}[1m])) == bool 0,
  good_minute = (ok_errors * ok_latency * ok_db * ok_probes) or ok_probes * 0
)
avg_over_time(good_minute[W:1m])
```

- `clamp_min(..., 1)` защищает от деления на ноль в минуту без запросов.
- `or vector(0)` нужен, потому что ряда с кодом 5xx может не быть вовсе.
- Если какой-то метрики в минуту нет (под `api` или база пропали), произведение пустое, и `or ok_probes * 0` записывает минуту как плохую. Минуты, когда не работает сам пробер, не считаются: это сбой мониторинга, а не сервиса.

**Общий SLO:** не меньше 99.5% хороших минут за 30 дней. Бюджет ошибок: 0.5% от 43 200 минут, то есть 216 минут (3.6 часа) в месяц.

### Бюджет ошибок и скорость его расходования

```
остаток бюджета = 1 - (1 - SLI) / (1 - SLO)
```

1 означает, что бюджет не тронут, 0 означает, что бюджет израсходован, а отрицательное значение означает, что SLO нарушен.

```
скорость расходования = (1 - SLI за последние 5 минут) / (1 - SLO)
```

Скорость 1 означает, что бюджет закончится ровно к концу 30 дней. Скорость 14.4 означает, что за час сгорает 2% месячного бюджета: по практике Google SRE это повод разбудить дежурного.

### SLA

SLA это внешнее обещание пользователям с последствиями при нарушении. Поэтому оно мягче внутреннего SLO: разница между ними дает команде время заметить расход бюджета и исправить проблему до того, как нарушится договор.

**SLA shorty:** доступность сервиса не меньше **99%** за календарный месяц. Доступность считается по общему SLI хороших минут, то есть это общий SLA для всего набора SLO: минута засчитывается, только если одновременно выполнены условия по ошибкам, скорости, базе и проверкам пробера. 99% месяца означает не больше 432 минут (7.2 часа) плохих минут.

| Доступность за месяц | Компенсация |
|---|---|
| 99% и выше | нет |
| от 95% до 99% | 10% стоимости месяца |
| ниже 95% | 25% стоимости месяца |

Не считаются нарушением: плановые работы, объявленные за 24 часа, и ответы 4xx на некорректные запросы клиента.

| | SLI | SLO | SLA |
|---|---|---|---|
| Доступность API | SLI-1 | 99.5% | |
| Скорость ответа | SLI-2 | 99% быстрее 250 мс | |
| База | SLI-3 | 99.9% минут | |
| Пробер | SLI-4 | 99.5% | |
| Хорошие минуты | общий | 99.5% | 99% |

## Графики

Графики построены в vmui (`http://localhost:8428/vmui`), несколько запросов на одном графике добавляются кнопкой «Add query».

1. **SLI за последнюю минуту:** SLI-1, SLI-2, SLI-4 с `W = 1m` и SLI-3. На них сразу видно, что происходит прямо сейчас.
2. **Общий SLI против SLO и SLA:** общий SLI с `W = 30m` и две горизонтальные линии, запросы `0.995` (SLO) и `0.99` (SLA).
3. **Хорошие минуты:** `good_minute` из запроса выше, ступенька 1 или 0 по минутам.
4. **Остаток бюджета ошибок:** `1 - (1 - SLI) / (1 - 0.995)` для общего SLI с `W = 30m`.

## Изменения поведения приложения для скринкаста

Чтобы показать реакцию SLI, в `api` добавлено управляемое ухудшение работы. Оно включается переменными окружения и по умолчанию выключено:

| Переменная | Что делает |
|---|---|
| `FAULT_ERROR_RATE` | доля запросов, на которые `api` отвечает 500, например `0.2` |
| `FAULT_DELAY` | задержка перед обработкой каждого запроса, например `400ms` |

`/healthz` сбои не затрагивают, иначе Kubernetes вывел бы поды из балансировки, и вместо ошибок `api` мы бы увидели ошибки nginx. Переменные меняются командой `kubectl set env`, после нее Deployment перезапускает поды.

Сценарий:

```bash
./k8s/slo/load.sh                        # в отдельном терминале, нагрузка около 8 запросов в секунду
```

| Шаг | Команда | Что меняется на графиках |
|---|---|---|
| 0. Норма | | все SLI равны 1, хорошие минуты идут подряд, бюджет не тронут |
| 1. Ошибки | `kubectl -n shorty set env deployment/api FAULT_ERROR_RATE=0.2` | падает SLI-1, пробер ловит 500 на проверке `redirect`, минуты становятся плохими, бюджет уходит в минус |
| 2. Медленные ответы | `kubectl -n shorty set env deployment/api FAULT_ERROR_RATE- FAULT_DELAY=400ms` | SLI-1 возвращается к 1, падает SLI-2 |
| 3. Падение базы | `kubectl -n shorty set env deployment/api FAULT_DELAY-`, затем `kubectl -n shorty scale statefulset/postgres --replicas=0`, через 2 минуты `--replicas=1` | падают SLI-3 и SLI-4. SLI-1 почти не меняется: запросы не доходят до `api`, их отклоняет nginx, и это видно только по проберу |
| 4. Восстановление | | SLI за минуту возвращаются к 1, а SLI за 30 минут остается ниже SLO и SLA: бюджет потрачен, и вернется он только по мере того, как плохие минуты выйдут из окна |

`FAULT_ERROR_RATE-` с минусом в конце удаляет переменную из Deployment.
