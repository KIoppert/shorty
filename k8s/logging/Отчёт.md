# Отчет: логи shorty в VictoriaLogs

## Что развернуто

Приложение shorty (namespace `shorty`: `api` на Go, `web` на nginx, PostgreSQL) работает в minikube. В тот же кластер, в namespace `logging`, развернуты:

| Файл | Что внутри |
|---|---|
| `k8s/logging/00-namespace.yaml` | Namespace `logging` |
| `k8s/logging/victorialogs.yaml` | VictoriaLogs single-node: PVC + Deployment + Service (порт 9428) |
| `k8s/logging/vector.yaml` | Vector: ServiceAccount + RBAC + ConfigMap с конфигом + DaemonSet |
| `k8s/logging/traffic.sh` | скрипт, который генерирует трафик и короткий сбой базы для демонстрации |

```bash
kubectl apply -f k8s/logging/
kubectl -n logging port-forward svc/victorialogs 9428:9428
# vmui: http://localhost:9428/select/vmui/
```

В VictoriaLogs v1.53 веб-интерфейс открывается по адресу `/select/vmui/`, путь `/vmui/` отвечает ошибкой.

## Формат логов

`api` и `web` пишут в stdout по одной JSON-строке на событие с полями из чек-листа семинара: `timestamp`, `level`, `message`, `service.name`. Для HTTP-запросов добавлены `method`, `path`, `status` и время ответа. Уровень зависит от ответа: 5xx дает `error`, 4xx дает `warn`, остальное `info`.

- `api`: ключи `log/slog` переименованы в `api/main.go`, уровень запроса выставляется в `api/http.go`.
- `web`: JSON-формат access-лога nginx задан через `log_format` в `web/nginx.conf.template`.

```json
{"timestamp":"2026-10-15T21:28:46.621Z","level":"error","message":"request","service.name":"shorty-api","method":"GET","path":"/healthz","status":503,"duration_ms":0.721}
```

## Почему Vector в DaemonSet

- **Приложение не знает про систему логов.** Оно пишет в stdout, а сбор и доставку берет на себя окружение. Чтобы поменять хранилище, не нужно трогать код.
- **Один сборщик на узел.** DaemonSet запускает один под Vector на ноде, он читает файлы всех контейнеров из `/var/log/pods`. С сайдкаром пришлось бы добавлять контейнер в каждый Deployment, и при масштабировании `api` росло бы и число сборщиков.
- **Собираются логи всех компонентов**, включая nginx и PostgreSQL, которые сами в VictoriaLogs отправлять не умеют. Прямой push из Go-кода покрыл бы только `api`.
- **Метаданные Kubernetes.** Источник `kubernetes_logs` сам добавляет имя пода, контейнера и узла.
- **Готовая интеграция.** VictoriaLogs принимает Elasticsearch bulk, а у Vector есть штатный sink `elasticsearch`. Параметры `_msg_field`, `_time_field`, `_stream_fields` задают, какие поля считать сообщением, временем и потоком.

Vector собирает только поды из namespace `shorty`, разбирает JSON и отправляет записи как есть. Текстовым строкам (PostgreSQL, служебные сообщения nginx) он проставляет `service.name` по имени контейнера и `level`.

## LogsQL-запросы

Перед запросами запущен `traffic.sh`: регистрация, неудачные входы, создание ссылок, переходы по ним с разной частотой, несуществующие коды. В конце скрипт на полминуты останавливает PostgreSQL, чтобы в логах появились настоящие ошибки.

### (а) Сырые записи за последние 15 минут

```
_time:15m
```

Все записи за 15 минут от всех сервисов, новые сверху. Видно, что JSON разобран на отдельные поля: у каждой записи есть сообщение (`_msg`), под (`pod`) и сервис (`service.name`). На скриншоте чередуются оба сервиса и обе реплики каждого: это регулярные проверки готовности, которые Kubernetes отправляет в поды `api` и `web`.

![(а) сырые записи](img/a-raw.png)

### (б) Фильтр по полям: ошибки api

```
_time:15m "service.name":"shorty-api" level:error
```

Только записи уровня `error` от сервиса `shorty-api`. Имя поля `service.name` взято в кавычки, потому что в нем есть точка. Все ошибки пришлись на время остановки PostgreSQL: `/healthz` отвечал 503, обычные запросы получали 500 с записью `internal error`. На гистограмме ошибки есть только около 15:18, то есть ровно во время сбоя.

![(б) ошибки api](img/b-errors.png)

### (в) `stats` с группировкой: сколько логов у какого сервиса и уровня

```
_time:15m | stats by ("service.name", level) count() as logs | sort by (logs desc)
```

`stats by` группирует записи по паре «сервис + уровень» и считает количество в каждой группе, `sort` упорядочивает по убыванию. За один запрос видно, кто сколько пишет и у кого есть ошибки: у `shorty-api` (сбой базы), у `shorty-web` (nginx отдавал клиентам те же 500) и у `shorty-postgres`. Уровень `warn` соответствует ответам 4xx: неверный пароль, занятый email, несуществующие ссылки.

![(в) stats по сервису и уровню](img/c-stats.png)

### (г) `top`: самые популярные короткие ссылки

```
_time:15m "service.name":"shorty-api" status:302 | top 5 by (path)
```

Ответ `302` означает успешный редирект по короткой ссылке, а в `path` лежит ее код. `top 5 by (path)` возвращает пять самых частых значений поля с числом вхождений. Получается рейтинг ссылок по переходам прямо из логов, и он совпадает с тем, как часто `traffic.sh` открывал каждую ссылку: `/go-doc` чаще всех, дальше `/k8s`, `/habr`, `/vlogs`, `/cv-pdf`.
